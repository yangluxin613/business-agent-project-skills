# 确认业务 Agent 项目需求

先读取用户给出的原始经历、已有需求文件和当前项目状态，判断本次只需 P00—P04 中哪一步。过往需求是业务背景，不自动改写为 Agent 产品。**从历史项目中的用户目标、业务对象、判断、资料和异常发散不同产品机会，不预设待办、审核或任务台。**所有 P02 候选都必须让业务人员在前端发消息、看到 AI 回复并能继续追问；对话中要有与业务任务相称的 Skill 和 MCP 能力落点。对话须产生可核实的业务结果，结果可以是有来源的解释、研判、方案、内容或经授权的业务动作；只有业务需要时才设计待办或审批。仅在用户要求完整需求确认时顺序推进到 P04；用户要求机会比较时停在 P02。

| 请求 | 参考文件 |
|---|---|
| 原始经历、业务地图、机会比较、选题基线（P00—P03） | [机会与基线](references/opportunity.md) |
| 角色、业务场景、人工边界、MVP 和业务验收意图（P04） | [业务产品与场景](references/business-product.md) |
| 产物、版本和跨 Skill 交接 | [需求包契约](references/handoff.md) |

把用户原文、推断、新产品假设和已确认决定分开记录；每个关键事实指向原文或用户答复。最多问五个真正会改变选题、主用户、专业责任或 MVP 的问题；其余缺口标假设并继续可独立完成的草案。涉及医疗、金融等专业决定时明确授权人员责任。用户确认过的决定不重复询问。

需求包的标准产物是项目工作区中的 source-experience.md、opportunity-comparison.md、requirements-baseline.md、scenario-and-acceptance.md、technology-requirements.md 和 project-state.md。已有等效文件可以复用，但在 project-state.md 指出路径、版本和确认依据。技术要求记录对话、多轮上下文、业务 Skill、MCP 及用户其余技术方向的覆盖期待、首个完整版本的必备能力和资源约束。**每项承诺接入的 AI 能力都要映射到至少一段业务对话：触发消息、介入点、影响回复或业务动作的方式、失败/越权时的表现及未来可核对的证据。**RAG、Memory、Context 等按场景使用，不要求每条消息全部调用；仅选型或不适用项写清理由。后台性能能力可由同一对话请求的 Trace/指标验证，不虚构独立页面按钮。这里不选择具体框架、MCP Server、API 契约或声称已接入；技术选型和合成验收数据由开发 Skill 负责。

完成前核对：旧项目事实与新项目设想可区分；候选是不同的用户任务和结果形态，而非同一种工单流程改名；主用户、任务、必要的人工决策、失败兜底和业务结果证据一致；场景给出可观察的业务通过/失败条件。P03 选题确认不自动覆盖 P04 新增的场景、结果证据和验收意图；这些内容须由用户审阅确认，并在 project-state.md 记录 P04 版本及确认原文位置。未满足时标“草案/待确认”，不可把文件存在当作已确认需求。交接只通过项目工作区文件，不把用户资料或密钥写入 Skill 目录。

用户**明确要求用模拟历史 PRD 跑全流程**时，可扮演虚构业务方分别给 P03 选题和 P04 场景作“模拟确认”，并记录模拟答复与依据；仅允许隔离的合成项目继续开发验证。状态、对外材料和交接文件始终标“模拟确认/合成试跑”，不得冒充用户本人或真实客户确认，迁移到真实项目时须重新走 P03/P04 门禁。
