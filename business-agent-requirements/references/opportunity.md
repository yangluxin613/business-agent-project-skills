# 经历、业务机会与需求基线（P00—P03）

在从过往经历启动项目，或重选业务方向时读取。只处理用户本次要求的步骤；已有确认的项目方向不因 Skill 被调用而重选。原始经历优先于先前 AI 摘要，记录到项目 `source-experience.md`；涉及个人或客户敏感信息时仅在当前工作区保留必要内容，对外材料按用户授权范围处理。

## P00—P01：从旧工作提取业务知识

逐项提炼行业、机构类型、真实用户、业务对象、任务频率、旧流程、非结构化资料、跨系统交互、人工判断、异常、权限、用户本人职责和可核实成果。再从这些材料找不同的业务任务：用户要理解什么、判断什么、解释什么、发现什么、规划什么、生成什么或执行什么；识别各任务的输入、专业边界和用户真正消费的结果。每条分别标来源原文、合理推断或待确认。区分“过去做过的需求”和“准备新建的 Agent 项目”；旧 HIS 接口、支付等需求只用来认识业务，不自动变成 Agent 产品。

产物为业务画像、跨项目业务地图、待探索痛点清单与初版证据台账。完成条件：能从原文追溯每个事实，且没有补造客户、接口、规模或指标。

## P02：业务 Agent 机会比较

提出 3—5 个**业务人员使用、以对话为可见入口**的相邻机会。先从历史项目证据生成机会池，再选择用户任务和结果形态有实质差异的候选；材料支持时至少覆盖三种方向，例如知识导航与解释、跨记录研判、方案比较与决策支持、内容生成、持续跟进或受控执行。方向是启发，不是必选清单；不能把“核查、审核、派单”换名称算成三个机会。每个候选必须写出：来自历史经历的线索与新增假设、用户第一条真实业务消息、AI 的具体回复、至少一轮追问或纠错、对话后用户可核实的业务结果；只读分析或解释可直接构成闭环，不强制创建任务。用户能在前端输入消息并看到 AI 回复。对话中标明拟调用的业务 Skill（任务能力、选择理由、输入/结果）、拟经 MCP 读取的业务系统 Tool/Resource（授权范围、返回内容、失败兜底）。对 RAG/知识检索、Context、Memory、多 Agent 等方向逐项给出自然的对话使用时机及计划阶段；若不适用，说明原因。P02 只比较能力方向，选中产品后 P04 才逐项映射承诺接入的技术。名称可以是业务能力或系统类型，不编造具体 Server、API 或已接入状态。缺 Skill/MCP 的自然业务落点或可行数据来源时重设计候选，而不是用空泛技术名凑数。

每个候选还写用户触发、目标、任务链、非结构化内容、条件分支、人工责任、前端可演示动作、数据可得性和风险。说明 AI 回复怎样由资料、工具结果和规则约束，用户如何追问/纠错，以及 Agent 相对普通聊天、搜索、表单和规则流程的必要性。按业务结果选前端承载方式，例如带引用的答案、证据时间线、对象关系视图、比较方案、可编辑内容或业务记录；不默认任务台。对话本身不是完成标准：只读场景以有来源、可复核、可用于业务判断的结果及用户反馈闭环；写入或对外动作以权限校验、必要的人工批准及回执闭环。仅研发自动化展示的候选应降权。

按用户任务价值、历史业务贴合、Agent 必要性、数据可得性、可交付性、风险可控性逐项给 0—3 分：`0 无证据或不适配 / 1 依赖重大未知 / 2 可用假设试验 / 3 有明确场景与可得输入`。分别说明评分依据；业务价值和贴合度优先于技术展示。完整技术覆盖与面试可解释性作为可行性检查和后续设计要求，不能为凑技术而抬高低价值候选。可按用户目标调权重，写出权重和排序理由，不把评分说成用户调研结果。产物为候选比较与推荐理由。

## P03：确认可执行基线

优先确认会改变选题的主用户、业务目标、用户要取得的结果、对话入口与多轮任务、事实权威来源、业务 Skill/MCP 的拟用范围、权限与需要人工决定的动作、最小闭环、失败处理和成功标准。最多询问五个关键问题，已回答的不重复问。若缺失不影响方向，可以标合理假设并继续做可评审草案；影响选题或专业责任边界的决定等待用户确认。

`requirements-baseline.md` 至少包括已知/推断/待确认、项目定位、对话及业务结果的完整闭环、MVP/非 MVP、业务/产品/技术指标、责任风险边界与最终选题理由；旧式 `P03-需求基线.md` 可作为细节文件，须在 `project-state.md` 映射。对话、业务 Skill 和 MCP 的目标验收条件与阶段需明确：早期 Mock 流程可作局部验证，不能当作真实模型/MCP 接入。完成条件：关键决定有用户确认或明确标成待确认；不能把“业务假设”写作“客户要求”。若用户只要求机会建议，交付 P02 即止。
