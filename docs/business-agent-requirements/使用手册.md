# 业务 Agent 需求确认 Skill 使用手册

使用 [business-agent-requirements](../../business-agent-requirements/SKILL.md) 将一项或多项过往业务经历转化为**面向业务人员的对话式 Agent 产品需求包**，负责 P00—P04。先从历史项目中的用户目标、资料、判断、异常和业务对象发散，再比较不同的产品机会；不预设待办、审核或任务台。每个候选都要有“业务人员发消息 → AI 回复 → 继续追问/纠错”的可见交互，并在对话中安排业务 Skill、MCP 与适用的知识等能力。结果可以是有来源的解释、研判、方案、可编辑内容或经授权的业务动作。旧需求用于理解行业和工作流，不直接改名为 Agent；本阶段不写代码或替开发阶段选框架。

## 怎样开始

在支持自定义 Skill 的 AI Agent 工具中导入完整的 `business-agent-requirements/` 文件夹，保留 `SKILL.md` 与 `references/` 的相对目录结构。若工具不支持目录导入，就把这些文件作为对话资料提供，并要求 AI 先阅读 `SKILL.md`、再按其中指引读取相关参考文件。在聊天中用自然语言说明要使用本 Skill；下方示例是对话消息，不是终端命令。具体导入和调用方式以所用工具的说明为准。

开始时尽量提供旧 PRD 原文、本人职责、目标用户和岗位、希望覆盖的 Agent 技术方向、可用资源及不能公开的事实。没有完整 PRD 也能先分析，但原文事实、推断和待确认项必须分开。不要把密钥或真实住户资料粘进提示词。

| 阶段 | 你要发出的请求 | 应得到什么 | 进入下一步的条件 |
|---|---|---|---|
| P00—P01 | 保存原文并拆解行业、角色、对象、流程、异常和本人职责 | `source-experience.md`、有来源的业务画像 | 旧经历与新产品假设没有混写 |
| P02 | 比较 3—5 个用户任务和结果形态不同、均有消息输入/AI 回复/追问的机会 | `opportunity-comparison.md`，每项含历史线索、示例对话、业务 Skill、拟用 MCP 能力和推荐理由 | 用户选择方向；推荐分数不等于市场调研 |
| P03 | 确认主用户、多轮对话任务、要取得的业务结果、必要的人机责任、MVP 和成功标准 | `requirements-baseline.md` | `project-state.md` 记录用户确认原文及版本 |
| P04 | 定义对话及页面业务路径、Skill/MCP 角色、异常、人工接管、结果证据和验收意图 | `scenario-and-acceptance.md`、`technology-requirements.md` | 用户**另行审阅并确认** P04 新增的对话、场景和通过/失败条件 |

项目工作区还应有 `project-state.md`，记录各文件路径、版本、草案/已确认状态和未决项。已有等效命名可保留，但要在状态文件中映射。P03 确认只覆盖选题基线，不能自动确认 P04。只有 P03 与 P04 两次确认依据都齐全，才把需求包交给项目开发 Skill（另行发布）。

如果明确要求用**模拟历史 PRD 跑全流程**，可以让 AI 扮演虚构业务方分别给 P03/P04 作“模拟确认”，并继续隔离的合成试验。状态文件和后续材料必须持续标“模拟”，不能把它替代真实用户/客户的两次确认。本手册下方提供完整的模拟物业旧项目 PRD 与分阶段使用示例。

## 物业旧项目完整试跑

下面是一位**模拟用户**粘贴给 AI Agent 的旧项目 PRD。它记录的是物业报修工单系统的历史需求，**不是**新 Agent 产品需求，也不代表真实物业客户、合同或运行数据。实际使用时，保留这种信息密度，替换为自己的真实经历，并区分“要求过”“本人做过”“实际验收过”。

### 第 1 条消息：原始经历与旧项目 PRD，执行 P00—P02

~~~text
请使用 business-agent-requirements Skill。请先执行 P00—P02：保存原始经历、拆解旧业务、提出 3—5 个面向物业业务人员的对话式 Agent 产品候选并评分。每个候选都要让用户发送业务消息、看到 AI 的有依据回复、继续追问或纠错，并能在对话中使用业务 Skill 和拟接入的 MCP 能力。到 P02 停止，不直接定选题、设计架构或写代码。把本条原文保存为 agent-project/source-experience.md。

【我的目标与资源】
我是一名程序员，目标岗位是 Agent 开发工程师。过去参与过物业报修工单系统的需求与开发，尚未在工作中做过 Agent。希望新项目服务物业客服、维修主管、维修人员或管家等业务人员。旧需求仅供你了解行业、数据、用户与流程；不要把“报修表单”“自动派单”或“工单回调”直接改名为 Agent。请从用户需要解释、研判、指导、沟通或协同的不同任务发散，不要预先限定为工单工作台。
希望产品方案覆盖 Agent/Loop/Skill/状态/Memory/上下文、模型与 Prompt/Tool Calling、Wiki/RAG/Embedding/重排/图谱、MCP/平台、推理性能、评估观测等完整技术方向。实际部署取决于本机资源和阶段目标。
可用：本地开发环境、合成住户与工单数据、Mock 服务；模型 API 可随后提供。未知：真实物业系统接口环境、住户数据授权、正式服务规则、客户试点、GPU 预算。
可以确认的经历：我参与过工单字段梳理、报修列表与详情页、状态接口和维修方回调处理。上线范围、真实单量、客户满意度和效率收益没有证据；对外材料不能自行补写。

【模拟旧项目 PRD：物业报修工单与维修服务系统对接】
文档性质：历史需求整理稿，记录计划实现和待确认事项；“计划验收”不等于“已验收通过”。

1. 业务背景与目标
住户通过物业 App、电话或前台提出报修。客服核对房屋与联系方式，登记问题并派给维修班组或外包服务商。维修人员处理后回填结果，客服回访或等待住户确认。旧项目要把报修登记、派单、处理回执和工单状态串起来，降低重复录入与漏跟进。它是工单管理需求，不含 Agent、语义知识检索或自动决定维修费用。

2. 角色与系统
住户：提出报修、补充问题描述、预约上门、确认服务结果；业主、租户和代报人权限是否不同，待物业方确认。
客服：核实服务对象、登记/查看工单、联系住户、审核关单所需记录。
维修主管：分派班组、处理超时与改派。
维修人员/外包商：接单、预约、上门、记录处理过程和材料。
物业经理：查看积压、超期和投诉风险。
住户档案/房屋系统：住户—房屋关系的候选权威来源；变更与授权口径待确认。
工单系统：记录报修、派单、处理状态与历史。
消息服务：可能发送通知；是否与旧系统集成、哪些消息需人工批准均未确认。
我的职责：梳理字段和状态、实现部分列表/详情交互、处理状态接口与维修方回调。没有证据证明我负责过全部业务运营或客户正式验收。

3. 旧业务流程
住户提出报修 → 客服确认房屋和联系方式 → 填问题类型、描述、照片与期望时间 → 形成工单 → 维修主管或规则分派 → 维修人员接单/预约/上门 → 回填处理结果和凭证 → 客服核对/回访 → 住户确认或按已确认规则关单。
电话报修的原话由客服记录；旧系统把它作为文本字段保存，并不会理解其含义。无法联系住户、照片不清、维修方拒单、重复报修、上门未遇、费用待审批、住户不认可完成结果时，旧需求要求保留状态与人工跟进，而不是默认关单。

4. 旧项目功能需求
FR-01 报修登记：录入工单号、房屋/楼栋、报修人、联系方式、问题类型、原话、图片、预约意向和记录人；哪些字段必填按服务类型与渠道确定。
FR-02 住户与房屋关联：从住户档案查询报修人与房屋关系；查不到、多人关联或代报时转人工核实，不能自动把工单关联到另一户。
FR-03 派单：维修主管查看区域、工种、值班和外包范围后分派。自动规则可以给候选人，但跨区域、紧急处置和费用批准由授权人员决定。
FR-04 维修进度：接单、联系、约时、上门、处理中、待材料、处理完成分别保留时间和责任人；回调乱序或重复时不覆盖更晚的有效状态。
FR-05 处理凭证：维修人员上传照片、处理说明、材料与费用草案。住户确认、客服回访和主管关闭的关系待确认；“维修人员点完成”不能直接等于住户认可。
FR-06 异常跟进：联系未果、改约、重复报修、拒单、跨部门协助、投诉升级需记录原因、下一负责人和下一次处理时间。
FR-07 审计和权限：记录创建、改派、状态变更、上传、回访和关单操作人；客服不能改写维修人员的原处理记录。保留期限、隐私展示范围和撤回机制待客户确认。

5. 字段、来源与缺口
房屋 ID/楼栋/单元/门牌：候选来源为房屋系统；历史迁移数据可能不一致。
住户 ID/报修人姓名/联系方式/身份关系：候选来源为住户档案或客服录入；代报人与实际住户要区分，展示范围按角色控制。
工单 ID/报修渠道/创建时间/工单状态：工单系统生成与维护。
问题类型/文本描述/图片/语音转写：住户或客服提供；图片是否可用于自动分类、语音是否可留存没有授权结论。
预约时间/值班人员/维修技能/外包范围：分别由预约记录、排班与服务商档案维护；数据是否实时待确认。
处理结果/维修照片/材料/费用草案：维修人员或外包商回传；费用审批结果不能由工单文本推断。
服务时限/升级规则/回访规则：旧会议纪要有讨论，但没有可发布的正式版本；不能补造具体小时数或赔付标准。

6. 旧接口与协作问题
IF-01 住户—房屋查询：查询键、返回多个房屋时的选择规则、租户和代报人权限待确认。
IF-02 创建/更新工单：幂等键与“创建成功但响应超时”后的状态查询方式待确认，不能盲目重建工单。
IF-03 维修方回调：外包商可能重复推送“已接单”，也可能晚到“上门中”状态；事件 ID、签名校验、时间排序与去重规则待确认。
IF-04 附件：图片大小、保留期限、访问授权和删除机制待确认。
IF-05 通知：短信或 App 消息是否由旧项目发送、由谁批准、失败如何补发都未确认。
没有真实地址、凭证、字段契约和 SLA 文档可供新 Agent 项目直接调用。

7. 计划验收与异常
AC-01 合成有效住户与房屋能创建报修工单，客服在列表和详情看到同一状态及历史。
AC-02 房屋关联不明、代报权限未知、关键字段缺失时不自动派单，提示人工核实。
AC-03 外包商重复/乱序回调不重复推进或倒退工单状态。
AC-04 创建请求超时且结果未知时先查原业务结果，不生成第二张相同工单。
AC-05 无住户确认或有效回访/主管依据时，不因维修方单方回填而误标“已关闭”。
AC-06 处理时长、逾期率和回访满意度的统计口径需物业方确认；目前没有实测数值。
这些是旧需求的计划验收，不是我已取得的生产成果。

8. 旧需求没有的内容
旧 PRD 没有理解多轮住户反馈、从多条服务记录中归纳根因、跨工单发现反复故障、检索版本化服务规则、提供现场知识导航、生成可核对的住户沟通说明、记忆住户沟通偏好或多 Agent 协作。如果你认为这些是新产品机会，标为“设计假设/待业务验证”，不能写成旧客户要求或本人以前实现过。

【本轮输出】
A. 保存原文到 source-experience.md；不要只存 AI 摘要。
B. 输出 P01 业务画像：原有用户、对象、流程、系统/数据、异常、我的职责；每个重要结论标“原文事实/推断/待确认”并指向原段落。
C. 先从旧 PRD 的业务对象、用户目标、资料和异常形成机会池，再输出 P02 候选表：尽量选择用户任务与结果形态不同的 3—5 项，不要用“待办/审核/任务台”填满候选。每项写历史线索与新增假设、业务用户、触发、首条消息、AI 的具体回复、追问/纠错、业务 Skill 选择及其输入/结果、拟通过 MCP 读取的授权系统事实与失败兜底、前端可见的业务结果。只读解释/研判可作为完整结果，不强制创建待办；写入或对外动作才设计授权与必要的人审。对 RAG/知识检索、Context、Memory、多 Agent 分别写自然的对话触发与计划阶段；无合理用途则写不适用理由，不为展示技术强行调用。说明 Agent 相比普通聊天、表单和搜索的必要性、数据条件与风险。按 Skill 的业务优先六维 0—3 分逐项打分并说明理由；未接入的能力只能写规划或 Mock。
D. 推荐一个候选，列最多 5 个会改变选题的问题。推荐仍是草案；到 P02 停止。
~~~

**你应该看到什么：**至少三个不同的物业业务机会，例如服务异常协同、跨工单故障线索研判、维修知识导航、住户沟通解释。它们分别交付协同行动、证据研判、现场指引、带引用的解释；**每个候选都能演示输入消息、AI 回复和追问**，且能指出对话中业务 Skill 与 MCP 分别承担什么任务。不能只给“自动派单 Agent、工单回调 Agent、报修表单 Agent”，也不能把“待办、审核、升级”换名字当成不同机会。某个推荐项目可以是客服使用的“物业服务异常协同助手”，但旧 PRD 未证明客户已经有跨渠道协同流程或愿意引入 Agent；它仍是新产品假设。评分要有分项理由。

每个候选还应有一段类似下面的**对话和能力落点**；这些是新产品设计示例，不是旧客户现有功能或已接入证据。

| 候选 | 业务人员发消息 → AI 回复 → 追问 | 对话中拟用的 Skill / MCP 与可核实结果 |

| 服务异常协同 | 客服：“W001 上门还缺什么？”→ AI：“缺房屋位置与可联系时间；工单原话与最近沟通有差异，请先核实。”→ 客服：“住户刚说周五下午可以，下一步？” | “补资料核查”Skill 整理缺项；拟经受限 MCP Tool 读取工单与沟通记录、经知识资源核对有效规则；回复附来源并生成待审核跟进草稿，客服批准后才建待办 |
| 重复故障研判 | 维修主管：“这栋楼近期反复报修的设备有哪些？”→ AI：“两张合成工单提到同一电梯，设备 ID 尚未核实。”→ 主管：“只看我负责的楼栋，并按时间展示证据。” | “故障线索关联”Skill 关联描述；拟经 MCP Tool 读取授权工单/设备档案；前端给证据时间线、来源与不确定项，不自动派单 |
| 维修知识导航 | 维修人员：“住户说电梯门关不严，我先核实什么？”→ AI：“先核实报修描述和设备标识；具体现场检查必须依据适用手册与安全规程，当前未取得。”→ 维修人员：“只列我能在到场前核对的信息。” | “排查路径导航”Skill 把现象映射到适用知识；拟经 MCP Tool 读取授权工单与设备资料；前端给带来源的检查路径，缺手册时明确停止专业指导 |
| 服务规则解释 | 客服：“W003 的处理情况该怎样向住户解释？”→ AI：“当前记录显示上门时间有争议；正式时限规则未取得，不能承诺处理时限。”→ 客服：“先写只包含已核实事实的说明。” | “事实与规则解释”Skill 区分已核实事实和规则；拟经 MCP Tool 读取授权工单/沟通记录和有效规则资源；前端给可编辑、带引用的说明，发送须另行授权 |

选中产品后，对承诺接入的能力再补一张**对话映射**。下表是物业候选的设计例，阶段和证据仍待开发时确认：

| 能力 | 对话触发与对回复的影响 | 失败时用户看到什么 | 后续如何证明 |
|---|---|---|---|
| RAG 检索 | 客服追问“现行规则要求核实什么？”；AI 只依据适用且有效的规则回复，并列规则来源 | 无有效来源时说明不能按规则判断，提示人工核实 | 同一对话请求的查询、权限过滤、召回/重排、引用与回复 Trace |
| Context | 客服第二轮说“只看这张 W001”；AI 保留本任务已确认的工单范围和上一轮缺项，排除其他工单 | 历史超预算或来源冲突时说明限制、追问或拒答，不默默丢条件 | 每轮上下文组成/压缩记录、Token 与回复差异 |
| Memory | 客服明确确认个人工作台偏好“先显示未核实缺项”；下一次会话可据此组织回复 | 偏好过期、越权或删除后不再沿用，并解释需重新确认 | 确认写入、跨会话读取、纠错/删除后重问的审计与回复对照 |

这些能力不要求每条消息都触发。若一个候选根本不需要长期偏好，就把 Memory 标后续或不适用，不把“有记忆模块”当作当前对话已使用的证据。
