# 业务产品与场景（P04）

读取用户已确认的 P03 基线；用户只要候选比较时停在 P02。这里确定业务行为与验收意图，不替开发环节做框架、数据库或接口选型。

## P04：业务产品与场景

明确名称、定位、价值主张、直接使用者、管理者、专家审核者、系统管理员、知识维护者、运营与最终受益者；没有实际职责的角色标“不适用”，不为填表造岗位。围绕所选用户任务设计高频、低频高价值、异常、复杂、多角色、人工接管、Agent 失败兜底及未来扩展场景；每个场景记触发、目标、输入、Agent 行为、知识/工具、分支、输出、必要的人审点、风险和可量结果。主场景及重要异常至少给一段两轮对话脚本：用户消息、AI 回复、追问/纠错、业务 Skill 选择、拟经 MCP 获取的授权事实、知识引用、可见业务结果；涉及写入、对外通知或专业判断时再注明批准人和状态变化。无资料、工具超时或越权时说明对话如何解释失败、追问或转人工。画出消息入站→权限→规划/Skill→MCP/知识→校验→AI 回复→用户取得业务结果→反馈/记忆/评估的主流程；有对外执行时增加授权/人工审核→执行→回执分支，标出超时、拒答、越权和适用的回滚。

写清 Agent、固定工作流、规则引擎及专业人员分别负责什么，特别是医疗/金融等领域的专业判断和不可逆操作。MVP 选一个能从对话输入完整走通的业务任务；前端按用户消费结果的方式选择引用答案、时间线、对比视图、可编辑草稿、记录页等形式，不固定为任务台；可同时有按钮和表单，但不能只有按钮触发分析。给每项承诺接入的 AI 能力建立“对话场景 ID → 用户消息/追问 → 能力介入点 → 对回复或行动的影响 → 失败/越权兜底 → 前端表现与后台待验收证据 → 引入阶段”映射。RAG 要说明何时检索及无有效来源的答复；Context 要说明跨轮历史、裁剪与来源冲突；Memory 要说明何时读、人工确认后何时写、纠错/删除后对下一轮答复的影响。无合理业务触发的能力标仅选型或不适用，不强塞进每轮对话。业务 Skill 和 MCP 在需求阶段只定义用户价值、权限边界及 MVP/后续位置，不代替开发阶段实现选型。其他场景分期。产物 `P04-产品与业务流程.md`。完成条件：主用户、主任务、必要的人工责任及成功标准与 P03 一致，异常路径有实际兜底，承诺接入的能力都能回指对话场景。


业务确认的交接：把角色、主任务、对话脚本、Skill/MCP 的业务职责、关键异常、必要的人工审核、业务结果证据及可观察的通过/失败条件写入项目的 scenario-and-acceptance.md；逐项引用 P03 决定或标假设。请用户审阅 P04 中新增的对话、场景、结果证据和业务验收意图；确认前保持草案，不能用 P03 的确认原文代替。需求包状态须记录 P03 与 P04 各自的文件版本和用户确认依据。
